# V5 — Generated Nations：8名の人格生成・実行前確認案

状態：入力文・出力schema・保存方法を具体化した設計資料。未実装・API未実行・人格未生成・未公開。2026-09-21作成。

## 1. 確定事項と提案の境界

**16軸＋C方式、8国家・8名Leader・各国家1000ポイント、国家とLeaderの独立生成、3層人格、展開の非脚本化は確定済み。** 本資料はその選択を再審議しない。

今回の実行候補は**8名の人物設定を生成・保存するところまで**。国家生成、対応付け、Simulation、人物の優劣評価、公開は含まない。生成時のschema細部・model・設定・費用の確認が済んでから、実行経路を実装・オフライン検証し、生成へ進む。以下の具体値は確認用の提案であり、既に採用したものではない。

| 項目 | 具体案 | 意味・別案との違い |
|---|---|---|
| 生成単位 | 1名につき新規contextで1回、最大8回 | 3層を同時生成する。自己紹介を別callに分けると最大16生成になるが、今回は採用候補にしない |
| 元入力 | [指示文全文](LEADER_GENERATION_PROMPT.txt)＋[出力schema](LEADER_GENERATION_SCHEMA.proposed.json) | 8回とも同じ本文。個人の配役や過去の生成結果を足さない |
| model | `gemini-3.6-flash`、Standard処理 | 既存Gemini系と同じmodel名。利用不能時に別modelへ自動変更しない |
| sampling | temperature `1.0`、candidateCount `1` | 1回の複数候補から好ましい人物を選ばない。topP/topKは指定せず、その事実を保存する |
| thinking | `LOW`、thought summaryの出力要求なし | 上限内で人物設定を作る案。内部思考の逐語記録を取得したとは扱わない |
| 出力上限 | 思考を含め1名8,192 token | 上限到達・途中JSONは失敗として保存。自動継続しない |
| 入力上限 | 実送信と同じ入力のcountTokens結果で1名16,000 token | 超過時は本文やschemaを削らず停止する |
| seed | APIへ指定せず、記録は`null`＋未指定理由 | 独立contextで8標本を得る案。同一出力の再生成保証はなく、元応答を固定して後続実験に使う。seedを固定する別案は送信前の仕様変更として確認する |
| 同時実行 | 1件ずつ | 最初の形式・通信エラー後に残りを連続失敗させない |
| 再試行 | 0回 | timeout・schema失敗を新しい人物で置き換えない |

公式資料でmodel名とstructured output対応を確認した。[model仕様](https://ai.google.dev/gemini-api/docs/models/gemini-3.6-flash)、[生成設定](https://ai.google.dev/api/generate-content)、[thinking](https://ai.google.dev/gemini-api/docs/thinking)。オンライン可用性とこのschemaの受理は未検証。

## 2. 各人物の出力

既存の[人格仕様](LEADER_PERSONALITY_PROPOSAL.md)を、応答用JSONへ整理した案。

| 層 | 生成する内容 | 形式の提案 |
|---|---|---|
| Layer 1 | 架空名・年齢・経歴・価値観・関係形成・葛藤/弱点・追加背景、および16軸 | 年齢は非負整数、各軸は0〜100整数。年齢上限や年齢の人数配分は設けない |
| Layer 2 | 本人が他国Leaderに語る自己紹介 | 日本語・一人称・200〜300文字程度の原文 |
| Layer 3 | 認識した条件、重視するもの、判断傾向、判断の進め方、例外/葛藤 | 1件以上の可変数。特定の状況一覧・件数・将来イベントは割り当てない |

経歴・価値観は各1件以上。葛藤/弱点の配列は空でも保持し、矛盾を強制作成しない。追加背景・原則の例外欄は`null`を許す。その他の文章欄は空白だけの値を形式不備として記録する。空欄を人間らしさの点数に置き換えない。

Googleが説明するJSON Schemaの対応範囲に合わせ、型・必須キー・配列・数値範囲等をschemaへ置く。空白だけの文字列、JSON重複キー、自己紹介の文字数等はローカルで検証する案。`minLength`等を遠隔側で必ず実施できるとは仮定しない。[structured output仕様](https://ai.google.dev/gemini-api/docs/structured-output)

### 内容を変更しない検証

- **停止する形式不備**：JSON不成立/重複キー、欠落・余分なキー、不正な型、16軸の範囲外、必須文章の空白のみ、原則0件。元応答は残す。
- **文字数の注記**：自己紹介は改行を除くUnicodeコードポイント数で計数し、空白・句読点を含む。200〜300から外れても自動的な切り詰め・失敗化・再依頼をしない。
- **再選別しないもの**：性格の矛盾、自己紹介との意味的不一致、似た人物、研究者が好まない価値観。各人物の形式合格と、人格の妥当性・人間らしさの評価を同一視しない。
- **別途確認するもの**：自己紹介での内部人格数値の列挙、担当国家/未発生イベントの設定混入。機械的に完全検出できるとは言わず、原文を保持して確認する。問題が見つかったら次の呼び出しとSimulation利用・公開を止め、勝手に修正しない。

人物間の多様性を保証するための再抽選、軸の正規化、相関調整、自由記述から別LLMで採点する工程は含めない。独立生成は統計的独立や偏りのなさの証明ではない。

### モデルに生成させない記録項目

generation ID、Leader ID、schema/prompt版、時刻、hash、model/usage、言語`ja`、想定読者、原則の識別子は、応答内容を変更しない記録層で付ける。原則IDは元配列位置とgeneration IDを参照する。これらの機械的情報をAIに創作させない。

## 3. C方式と公開範囲

C方式は確定済み。今回の人物生成は**元の16軸・人物文・自己紹介・原則を保存する工程**であり、Simulation入力への変換は行わない。

数値を自然言語へ変換する細部は、Simulation開始前に確認する。候補は、(a) 軸の定義と元値を定型文で説明する方式、(b) 強度帯を文章化し元値も併記する方式。前者は新たな強度境界を設けず、後者は読みやすい一方で区切りと語調が追加の入力条件になる。今回はどちらも実装しない。これを未決定のまま残しても、元人格の生成・保存は分離して実行できる。

本人の内部設定と他国に届く自己紹介を分離する。生成時の設定ファイル全文を他国へ流さない。自己紹介の世界内配信タイミング、公開プロフィール、国家との対応付けは後続設計の確認事項であり、この8回に便乗して確定しない。

## 4. 呼び出し数・時間・費用確認

予定は**最大8回の生成＋最大8回のcountTokens照会＝最大16回のAPI要求**。countTokensは生成要求と別集計する。追加の接続テスト、修復用LLM、評価LLM、モデル自動切替、Web検索は含めない。今回の資料作成で行ったAPI要求は0回。

8回直列の所要時間は生成応答を1件30〜120秒と仮置きすると4〜16分。保存・検証・内容確認を含め15〜30分程度を見込むが、**この3層人格の生成速度は未実測**。これは承認後の生成工程の見込みであり、実行経路の新規実装・オフライン検証時間を含まない。接続30秒、読込180秒をtimeout案とし、遅延時に残りを自動実行しない。

入力本文・schemaのオフライン実サイズと、出力/思考tokenの仮定を使った費用見積は、公開資料に混ぜない確認用メモへ別保存する。承認時にはモデル、処理種別、単価の確認日、入力上限、出力上限、最大生成回数、USD停止枠を実行設定として固定する。利用者の残高・入金額・開発相談は実験入力にも公開Evidenceにも含めない。

## 5. 技術障害を連鎖させない実行案

V4の`request_body`はV4 promptと設定に結び付いており、V3の生成経路もV3専用の応答検証を持つ。片方の入力設定だけをコピーし、他方の送信・検証へつなぐ方法を採らない。これは既存コードの読み取りで分かった互換性上の注意であり、過去の10run障害原因を新たに断定したものではない。

承認後に準備するV5専用経路は、既存V1〜V4のruntimeを変更しない。まず偽の通信先を使い、実際に送る予定の本文が保存・token見積対象と一致することをオフラインで確認する。

1. prompt/schema/model/configと送信予定bodyを凍結し、保存が成功してから外部要求へ進む。
2. 1人目の入力だけcountTokensへ送り、結果を保存する。上限超過・応答不備なら生成0回で停止。
3. 正確に同じ入力・設定の生成要求を1回送る。送信前にその要求の最大見積額を予約記録へ置く。
4. 生の応答bytes、HTTP status、取得時刻を**JSON解析前に**保存する。認証header・秘密鍵を保存しない。
5. 応答完了、候補が1つ、schema・内容存在・usage・Evidence整合性を確認する。数値の矛盾を解消しない。
6. 問題がなければ同じ手順で次の人物へ進む。前の人物の情報を次の入力へ追加しない。
7. 8回終了か、最初の通信/形式/保存エラーで停止する。無応答時は課金不明として予約を保持し、0円扱いも再送もしない。

`MAX_TOKENS`、候補0/複数、非JSON、JSON重複キー、型や範囲の不正、HTTPエラー、timeout、usage不明、保存失敗で残りの実行を止める。元RAWが保存できない障害なら受け取ったデータの所在と未保存状態を報告し、成功と呼ばない。schemaを緩めたり本文を変更したりしてその場で再試行しない。

実装時のオフライン確認対象は、正しい送信body、8件のcontext分離、上記失敗後の追加要求0件、9件目拒否、失敗RAW保持、既存Evidence検証器との互換性。**これらのruntime確認は未実施**であり、今回は設計ファイルだけを確認した。

## 6. Evidenceの保存案

[Evidence Format 1](../../architecture/EVIDENCE_FORMAT_V1.md)を継承。作成時に空の人物Evidenceや架空の成功記録を置かない。承認後の実行は非公開の独立した出力領域へ保存し、既存resultsへ上書きしない。

```text
<batch-id>/
  plan.json                         # 確認された実行設定と8件の予定ID
  <generation-id>/
    manifest.json                   # model/config、prompt/schema hash、seed=null等
    RAW/
      count.request.json
      count.response.json           # HTTP応答原bytesのbase64表現とstatus
      generation.request.json       # 実送信body。認証headerを除く
      generation.response.json      # 解析前の応答原bytesのbase64表現とstatus
      failure.json                  # 失敗時のみ。取得不能は取得不能と記録
    terminal.json                   # success/failure/interruptedとhash
    DERIVED/
      persona.json                  # 元response参照＋正式人物設定と3層
      validation.json               # 範囲・型・文字数・その他確認結果
```

RAW内の各JSONは既存の`sha256`/`payload` wrapperに従う。HTTP原bytesはbase64で保持し、復号bytesのhashも記録する。HTTP応答全体をそのまま画面へ表示しない。

RAW全体は相対ファイル名→byte hashの既存方式で集約し、terminalとmanifestへ接続する。生成物の変更や再依頼が必要なら別attemptで記録し、元RAWを更新しない。生成した架空Leader名と、利用者・制作相談の名前を混同しない。

費用・予約記録は非公開の実行記録として管理する。公開対象は後日明示的に選びsecret/privacy scanを通す。公開しない記録を削除してから元のEvidence hashが一致すると主張せず、必要なら別の公開manifestと元記録への来歴を作る。今回は公開用の抽出も行わない。

## 7. 今回の停止地点

本資料・prompt・schemaと非公開の費用見積を提示して停止する。**16軸＋C方式への再確認ではなく、今回具体化した生成設定・形式・呼び出し枠の確認地点**である。

次の確認でこの生成案が承認された場合は、V5専用経路のオフライン検証を完了してから、最大8名分の生成へ進める。重要な不一致や技術障害が見つかった場合は停止する。国家生成・Simulationを同じ承認へ含めない。
